# ADR-008: npm (Package Registry and Manifest)

## Status

Accepted

## Context and Problem Statement

The team needs a standard for how JavaScript and TypeScript packages are consumed and published. Inconsistent use produces real operational harm: a floating dependency range lets a malicious version ship to production, a missing lockfile turns "works on my machine" into a daily problem, an absent `exports` field breaks TypeScript consumers, a leaked `.env` inside a published tarball exposes secrets, and publishing from a developer laptop forfeits provenance attestations. We need conventions covering how packages are declared, locked, installed, and published so `npm install` produces identical dependency trees everywhere and publishes are verifiable.

## Decision Drivers

- Reproducibility: lockfile + frozen installs in CI ensure identical dependency graphs across environments
- Security: OIDC-based CI publishing with `--provenance`, 2FA on registry accounts, dry-run verification
- Correctness: `exports` maps with `import`, `require`, and `types` conditions serve all consumer toolchains
- Hygiene: `files` field restricts publish payload; `npm audit` gates on high-severity findings

## Considered Options

- npm with full manifest conventions, lockfile, frozen CI installs, and OIDC provenance publishing
- npm with ad-hoc version ranges, no lockfile, and manual publishing from developer laptops
- Yarn (Classic or Berry) as the package manager
- Bun as the package manager

## Decision Outcome

We will use npm as the package registry standard for all JavaScript/TypeScript packages. Every package declares explicit `name`, `version`, `description`, `license`, `repository`, and `type` fields. Scoped names (`@org/name`) are used for organization-owned packages. Semantic Versioning is followed. Breaking changes bump the major version. Dependencies use explicit version ranges (no `*` or `latest`). Exactly one lockfile is committed per project. CI installs use `npm ci` (or the package manager equivalent with frozen lockfile). `exports` maps declare `import`, `require`, and `types` conditions. The `files` field restricts the publish payload. Packages are published from CI with OIDC and `--provenance`. `npm audit --audit-level=high` is a CI gate. Multi-package repos use the package manager's native workspaces feature.

## Consequences

- Positive: frozen lockfile installs eliminate dependency graph drift between environments
- Positive: OIDC provenance publishing provides verifiable supply-chain attestation
- Positive: `exports` maps ensure all consumer toolchains (ESM, CJS, TypeScript) resolve correctly
- Negative: OIDC publishing setup requires per-registry configuration
- Negative: maintaining the `files` field requires discipline to avoid publishing unwanted files or missing required ones
- Neutral: publishing from developer laptops is forbidden
