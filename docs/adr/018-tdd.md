# ADR-018: Test-Driven Development (Red-Green-Refactor)

## Status

Accepted

## Context and Problem Statement

The team needs a development workflow that produces a test suite developers trust enough to rely on for regression detection. TDD's value depends entirely on the order of operations: write a failing test, make it pass with minimum code, refactor under a green suite. Skipping the red step, batching tests ahead of implementation, or refactoring while red silently converts "TDD" into "tests written later" — which looks the same in the diff but gives up the regression safety, design pressure, and executable-specification properties that justify the practice. We need a cycle discipline that is verifiable from commits and behavior.

## Decision Drivers

- Regression safety: writing the failing test first proves the test can catch the defect; adding tests after the fact does not
- Design pressure: writing tests before implementation drives dependency injection, testable interfaces, and smaller units
- Executable specification: tests written to describe behavior (not implementation) serve as living documentation
- Bug discipline: every bug fix must be preceded by a failing test that captures the regression

## Considered Options

- Red-green-refactor TDD: failing test first, minimum implementation, refactor under green
- Test-after development: write tests after implementation
- No test discipline: write tests when there is time or when CI requires coverage
- Behavior-Driven Development (BDD) as the primary development loop

## Decision Outcome

We will use red-green-refactor TDD as the standard development workflow. Every failing test is written and run before any production code that changes observable behavior. The failure is verified as an assertion failure (not a syntax error). Minimum production code is written to pass the current failing test. The full suite must be green before refactoring. Refactors do not change observable behavior. Each cycle targets under ten minutes; longer cycles revert to the last green commit and split the problem. Commits happen only at green states. Every reported bug gets a failing test before the fix. Tests are named after behavior, not function names.

## Consequences

- Positive: every production behavior has a test written to catch its absence before the implementation exists
- Positive: TDD pressure on testability results in better-factored code with explicit dependencies
- Positive: committing only at green states produces a history where every commit is verified
- Negative: TDD requires discipline and practice to sustain; it is slower in the short term than writing code first
- Negative: the approach requires team buy-in; mixed discipline produces an unreliable test suite
- Neutral: tests written after the fact, disabled tests without tracking issues, and commits at red states are all forbidden
