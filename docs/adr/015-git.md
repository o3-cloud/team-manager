# ADR-015: Git Conventions

## Status

Accepted

## Context and Problem Statement

Git is the substrate every other practice in this layer relies on — Conventional Commits ([ADR-013](013-conventional-commits.md)) parses messages git stores, MADR/BDR ([ADR-016](016-madr.md), [ADR-011](011-bdr.md)) ride PR review, TDD's "commit at green" only means anything if the history shows it. Without shared rules for branch model, merge strategy, signing, force-push, tags, large-file handling, and hook installation, every other practice silently degrades: force-pushes to `main` rewrite the audit trail release tooling depends on, merge commits with WIP commits bury machine-parseable commits, and contributors who skipped hook installation bypass the local lint gate. We need a single authoritative convention covering branch model, naming, merge strategy, signing, rewrite policy, hook ownership, and recovery.

## Decision Drivers

- History integrity: linear history with signed commits and immutable tags makes the audit trail reliable and verifiable
- Tooling alignment: trunk-based development with squash-merge produces one Conventional Commit per PR, enabling automated releases
- Security: commit and tag signing provides cryptographic provenance; protected-branch rules prevent bypasses
- Consistency: declarative hook management ensures every contributor runs the same gates locally

## Considered Options

- Trunk-based development with squash-merge, signed commits, protected `main`, declarative hook management via hook manager
- GitFlow with `develop`, `release`, and `feature` branches
- GitHub Flow with merge commits and no signing requirement
- Ad-hoc conventions per team member

## Decision Outcome

We will use `main` as the default branch with trunk-based development ([ADR-019](019-trunk-based-development.md)). Exactly one merge strategy (squash-merge or rebase-merge) is configured per repo; the forge forbids the other. Every commit and tag is signed (GPG, SSH, or Sigstore). Force-pushes to `main` and shared branches are forbidden; `--force-with-lease` is the only permitted force-push on personal branches. Releases are annotated signed tags following the project's SemVer scheme. The `.gitignore` and `.gitattributes` are committed. Large binaries use Git LFS. Git hooks are managed declaratively via a hook manager committed to the repo. Branch protection rules are stored as code. `git commit --no-verify` is forbidden.

## Consequences

- Positive: signed commits and tags provide cryptographic provenance; release tooling can trust the audit trail
- Positive: declarative hook management ensures no contributor can accidentally skip local quality gates
- Negative: signing setup requires every contributor to configure GPG/SSH key and the forge to verify signatures
- Negative: squash-merge discards intermediate commits; contributors must write a good final commit subject
- Neutral: force-push to `main`, merge commits on `main`, and hook bypass via `--no-verify` are all forbidden
