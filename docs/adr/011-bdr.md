# ADR-011: Behavior Decision Records

## Status

Accepted

## Context and Problem Statement

ADRs capture *how* the system is built, but they do not describe *what the system must do for users*. Without a separate record of externally observable contracts, behavioral intent is reconstructed by reading code and tests — conflating implementation with promise, letting behavioral scope creep silently, and making regressions invisible until users notice. We need a complementary record format that captures individual capabilities the system agrees to uphold, with acceptance criteria a black-box observer can confirm and Given/When/Then scenarios that drop directly into integration tests.

## Decision Drivers

- Separation of concerns: ADRs describe architecture; BDRs describe user-observable behavior
- Machine-checkable contracts: Given/When/Then scenarios should be directly executable as integration tests
- Regression prevention: immutable `Accepted` BDRs make behavioral regressions detectable without reading internal source
- Alignment with BDD: the format is black-box by design, forcing acceptance criteria to be implementation-independent

## Considered Options

- Behavior Decision Records (BDRs) in `docs/bdr/` with a fixed section layout
- Embedded behavioral specs within ADRs
- Cucumber/Gherkin feature files as the behavioral contract
- No formal behavioral record (rely on test descriptions)

## Decision Outcome

We will store BDRs in `docs/bdr/` following the same numbering and lifecycle conventions as ADRs ([ADR-016](016-madr.md)). Each BDR names a single capability, carries a `## Status` section, a `## Behavior` section (one sentence, black-box), a `## Context` section, an `## Acceptance Criteria` section (implementation-independent), and a `## Verification` section with Given/When/Then scenarios. The body of an `Accepted` BDR is immutable. Behavioral changes require a new BDR that supersedes the prior one. An index `README.md` lists all BDRs by number, title, and status.

## Consequences

- Positive: BDRs provide machine-checkable behavioral contracts distinct from architectural decisions
- Positive: Given/When/Then scenarios are directly usable as integration test scaffolding
- Positive: immutability of `Accepted` BDRs makes behavioral regressions clearly visible
- Negative: maintaining a separate BDR directory alongside ADRs adds documentation overhead
- Neutral: behavioral requirements described only in ticket comments or test descriptions are insufficient under this decision
